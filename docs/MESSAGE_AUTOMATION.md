# 공식 재난문자 자동 수집·분석

간소화 2단계 구현 기준이다. 사용자는 2026-11-08 제한 운영 배포를 승인했고 현재 배포 전 검수 중이다. **운영 미배포·자동 수집 비활성**이다. 기존 SafetyData 이용승인과 인증키를 찾았으며,
소유자 실행 결과에서 GCP `SAFETY_DATA_API_KEY:1`과 runtime 읽기 역할 추가, Cloud Shell의 빈 API 응답을 확인했다.
이어진 비공개 임시 Cloud Run 검수에서 오늘 전국/부산 문자, 날짜/지역/페이지 기본 조건과 실제 키 사용을 확인했다.
사용자는 일일 호출 한도를 **500회**로 확인했다. 이에 맞춰 전국 일괄 조회·15분 주기·최근 24시간 450회 공통 상한을 구현했다.
운영에는 아직 배포하지 않았다. 과거 날짜 경계/제공 지연·이용 조건과 실제 정규 예약 실행 확인은 남았다.
가짜 제공자 검증과 실제 API 계약·IAM·예약 실행 검증을 구분한다.

## 사용 흐름

연결 후에는 휴대폰으로 받은 문자를 전달할 필요 없이 행정안전부의 공개 API를 서버가 조회한다.
공식 문자 ID로 저장하고 새 원문 버전을 분석 대기열에 넣는다. AI가 원문을 해석하고 필요한 장소·주변 시설 도구를 선택한다.
분석 결과를 저장한 뒤 관리자가 대기함을 열면 추천 위치·시설·안내 초안이 함께 표시된다.
정상 건의 주요 조작은 **기록 열기 → 이 내용으로 검토 완료**다. 안내문 복사는 필요할 때 추가한다.

브라우저는 수집을 시작시키지 않는다. 화면은 60초마다 상태를 읽고, 대기함에 있을 때 목록도 갱신한다.
열어 둔 기록이나 미승인 입력은 자동 갱신으로 덮지 않는다. 분석 중 기록의 새로고침은 읽기 요청이다.
실제 전파·시설담당자 연락·현장 회신은 이 기능에 포함하지 않는다.

## 수집 범위와 실패 처리

- 기본 **15분 주기**로 전국 자료를 날짜별로 한 번씩 받고, 실제 수신지역이 소관 5개 광역지역에 걸치는 문자만 저장한다.
  전국 대상 문자는 포함하며, 지역이 모호한 행은 누락 가능성을 표시한다. 본문 지명만으로 지역을 만들거나 관련 없는 지역을 저장하지 않는다.
  정상 시 오늘·전일 겹침 조회다. `crtDt`가 정확한 하루 또는 해당 날짜 이후를 반환하더라도 날짜 범위를 검증하고 공식 ID로 중복 방지한다.
  원문 발행 시각과 API의 실제 수신지역을 보존한다.
- 회당 최대 **4페이지·100건/페이지·120초**이며, 남은 날짜/페이지/행 위치를 저장해 재개한다.
  수동 조회 UI의 3페이지 상한을 사용하지 않는다. 페이지 내용이 달라지면 행 위치를 초기화하고, 여러 페이지의 마지막에서 첫 페이지도 대조한다.
  페이지 정렬이 바뀌는 REST 조회의 완전한 원자적 snapshot을 보장하는 것은 아니다.
- 중단 후 마지막 완료일부터 기본 최대 7일 범위로 보충한다. 부분 조회 중 며칠 중단돼도 중간 날짜를 추가한다.
  창을 넘어선 누락 가능성은 `partial`로 남기며 정상 완료 시각을 앞당기지 않는다. 설정 범위를 늘려 재조회하거나 별도 복구 범위를 검토한다.
  정상 운영에서 전일보다 오래 지연 도착한 문자는 기본 겹침 범위 밖이다. 실제 제공 지연·보관 기간·쿼터에 맞춘 활성화 검증이 필요하다.
- 최초 시작 시각을 영구 저장한다. 기본은 첫 활성화 시각이며 과거 자료를 한꺼번에 분석하지 않는다.
  시작 전의 이미 알려진 공식 ID는 정정 여부를 확인한다. 시작 후 발행 또는 이미 분석했던 기록의 새 버전만 대기열에 넣는다.
  재배포나 설정 변경만으로 최초 시작 시각을 되돌리지 않는다.
- 같은 ID·동일 원문은 새 검토 버전/분석을 만들지 않는다. 최신 관측 시각만 별도로 갱신한다.
  원문 변경은 새 원문 버전/재검토로 남기며 이전 분석·완료·초안은 이력에 보존한다.
  이전 조회 결과가 최신 내용을 덮지 못하도록 관측 시각을 트랜잭션에서도 확인한다.
- 등록 후 대기열 저장 전에 중단돼도 같은 페이지 재조회로 복구한다. 원문/시각/행을 해석하지 못하거나 API 조회가 실패하면
  이전 기록·마지막 정상 시각을 보존하며, 오류를 `문자 없음`으로 표시하지 않는다.

## 문자 조회 상한과 분석 한도

사용자가 확인한 공식 API 한도는 하루 500회다. 앱은 **최근 24시간 최대 450회**까지만 외부 요청을 시작하며 50회를 외부 점검 등에 남긴다.
달력 자정에 사용량을 초기화하지 않고 24시간 이동 창으로 제한해 자정 직후의 집중 호출도 막는다.
이 제한은 다른 앱이나 사용자가 직접 실행한 API 요청을 관찰하지 않는다. 별도 사용량이 여유분을 넘는 경우 제공자 한도에 먼저 걸릴 수 있다.

자동 수집과 관리자 수동 공식 조회는 같은 Firestore 요청 기록을 사용한다. HTTP 전에 트랜잭션으로 차감하고, 실패/타임아웃도 집계한다.
저장소를 확인하지 못하면 외부 요청을 시작하지 않는다. 리디렉션을 따라가 한 번의 예약으로 여러 API 요청을 보내지도 않는다.
한도가 차면 진행 위치·마지막 정상 자료를 보존하고 이전 요청이 24시간 창을 벗어난 뒤 이어간다. 수동 조회는 429와 재조회 시각을 반환한다.
화면에는 최근 24시간 조회 횟수/450과 한도 대기·재조회 가능 시각을 표시한다.

정상 15분 예약은 하루 96회, 1회 최대 4페이지이므로 자동 조회 계획은 최대 384회/일이다. 단순 첫 페이지 기준은 192회/일이다.
추가 페이지/첫 페이지 대조도 4페이지에 포함한다. 수동 조회·중복 실행·실패를 포함한 실제 앱 전체 상한은 위 450회 이동 창으로 막는다.
자료가 많거나 장애가 길면 여러 회차에 나누어 수집하므로 조회 간격이 전체 자료 확보 지연의 상한을 뜻하지는 않는다.

수동·자동·상세 분석 API가 Firestore의 **동일한 일일 시작 횟수와 동시 실행권**을 사용한다.
기본 20건/한국 날짜, 설정 범위 1~100건이다. 실패·중단된 시작도 보수적으로 집계한다.
건당 기존 최대 6회 모델 응답·80초 예산과 프로세스 내 간격/시간당 제한을 유지한다.
따라서 일일 건수는 모델 요청 횟수나 금액 상한 자체를 뜻하지 않는다. 실제 사용량을 보고 일일 건수를 정한다.

자동 분석은 1분마다 최대 1건을 처리한다. 한도/다른 실행 때문에 시작하지 못한 건은 대기 상태로 보존한다.
24시간 넘게 기다린 건은 유료 분석을 자동으로 시작하지 않고 수동 확인 대기로 옮긴다.
제공자 실패나 실행 중단으로 결과가 불확실한 건은 자동 재시도하지 않는다. 관리자가 기록을 열어 명시적으로 재분석할 수 있고 같은 한도를 사용한다.
분석 시작 전 원문 버전별 시도 표시를 저장하고, 만료된 실행권을 복구할 때 저장된 성공 결과를 우선 확인한다.
원문이 바뀌거나 다른 분석 실행이 시작되면 이전 결과를 현재 버전에 붙이지 않는다.

## 실행·저장 경계

```text
별도 예약 조회 → safety-message-worker /collect → 원문·원문 버전 + 대기열
별도 예약 분석 → safety-message-worker /analyze-next → 한도 예약 → AI 해석 저장
관리자 API /automation + 목록 → 상태·검토 대기함 → 한 화면 검토·승인
```

기존 worker 이미지와 같은 코드베이스를 사용하되 `safety_dashboard.operations.message_worker:app`으로 실행한다.
새 서비스 `safety-message-worker`는 IAM 비공개·최소 0/최대 1 인스턴스·동시 2·180초 제한이다.
`safety-message-collect`(기본 15분), `safety-message-analyze`(1분)의 OIDC 예약 작업은 기존 예약 계정을 사용하고 자동 HTTP 재시도는 0회다.
worker에는 OpenAI/Kakao/SafetyData의 고정 버전만 연결한다. 관리자 비밀번호·KMA·Telegram·SMS 키는 연결하지 않는다.
공개 API에는 두 실행 경로가 없고, 기존 KMA `dispatch`와 자동알림 상태를 호출·초기화하지 않는다.

기록은 기존 `disaster_message_reviews`에, 진행 상태·대기열·실행권·한국 날짜별 집계는
`disaster_message_pipeline`에 저장한다. 대기열은 단일 `queue_key` 필드 범위 조회로 처리하므로 추가 복합 색인이 필요 없다.
문자 조회 상한은 같은 컬렉션의 `official-request-budget` 문서에 시각만 저장하며, 원문/키를 저장하지 않는다.
운영 저장소 오류 때 메모리로 대체하지 않는다. 실행권은 300초이며 소유자가 바뀐 뒤 이전 실행이 상태를 덮거나 실행권을 풀 수 없다.

화면 상태는 꺼짐/키 필요/연결 검증 필요/첫 실행 대기/정상/부분/지연/조회 오류/저장소 확인 불가를 구분한다.
마지막 정상/시도 시각, 분석 대기·실패·수동 확인 건수와 오늘 시작 횟수를 함께 표시한다.
`live`는 설정된 API 조회 범위를 완료했다는 뜻이며 모든 실제 재난문자의 즉시 수신을 보증하지 않는다.

## 실제 연결의 남은 시작점

사용자 캡처에서 [행정안전부 긴급재난문자](https://www.safetydata.go.kr/disaster-data/view?dataSn=228)의 기존 `승인` 상태를 확인했다.
회원정보에서 기존 키를 찾았고, 사용자는 GCP Secret 생성도 확인했다. **키 값은 채팅·GitHub 파일로 보내지 않는다.**
이용신청이나 키 생성을 반복하지 않고 등록된 Secret을 점검한다.
기존 OpenAI/Kakao 키는 GCP Secret Manager 버전 1로 준비돼 있으므로 다시 발급하지 않는다.

연결 작업자는 다음을 순서대로 수행한다. 이 문서는 활성화 승인을 대신하지 않는다.

1. Secret Manager `SAFETY_DATA_API_KEY`는 소유자 실행 결과에서 버전 **1**과 runtime 읽기 역할 추가를 확인했다.
   현재 GitHub 점검 계정은 해당 메타데이터를 조회할 권한이 없다. 소유자가 Cloud Shell에서
   [점검 도구](../scripts/check_safetydata_connection.py)를 고정 commit으로 내려받아 `--grant-runtime`으로 실행한다.
   이 옵션은 해당 Secret에만 `safety-dashboard-runtime`의 `roles/secretmanager.secretAccessor`를 부여한다.
   ENABLED 버전을 조회해 고정한 뒤 값을 Cloud Shell 메모리 안에서만 사용해 오늘 대구 지역 1페이지/1건을 1회 조회한다.
   원문/키/원본 오류를 출력하거나 파일로 저장하지 않으며 재시도·배포·수집 시작·DB 쓰기·AI/장소/발송 호출을 하지 않는다.
   이 준비 명령은 이미 실행했으므로 반복하지 않는다. `passed`/`valid_empty_response`는 소유자 Cloud Shell의 1회 빈 응답 확인이다.
   이어서 [실제 서버 검수](evidence/2026-11-08/safetydata-registration-preflight/runtime-check.json)에서 동일 runtime·버전 1로 4회 조회해 기본 검사를 통과했다.
   당일 2페이지와 부산 지역의 제한 표본이며 과거 날짜 경계·장기 제공 지연·상시 운영을 대신하지 않는다.
   추가 진단이 필요할 때 기존 메타데이터 워크플로의 `mode=official-feed`를 명시적으로 실행해 비공개 임시 서비스에서 최대 6회 읽기로
   전국 최근 자료·날짜/지역 조건·요청 페이지 크기·페이지 간 ID 겹침·첫 페이지 변화를 대조한다. 최근 3일이 모두 비면 날짜 없는 대조 1회만 한다.
   결과에는 조건·건수·필드 존재/검사 여부만 담는다. 원문/ID·키는 내보내지 않으며 운영 DB/AI/발송과 연결하지 않는다.
   임시 서비스는 항상 삭제하고, 실제 기능 배포와 구분한다.
   `MESSAGE_REVIEW_FEED_ENABLED=true`, `MESSAGE_REVIEW_FEED_VERSION=<고정 숫자 버전>`으로 수동 읽기만 먼저 준비한다.
2. 기본 샘플 날짜/지역/페이지·중복·빈 결과/수신지역은 제한 읽기로 확인했다. 과거 날짜와 자정·정렬 변화·오류/지연·계정 쿼터·이용/보관 조건을 추가 대조한다.
   사용자의 실제 일일 한도 500회에 맞춰 지역별 5분 조회를 전국 일괄 15분 조회와 공통 450회 제한으로 바꿨다.
   공개 문서의 플랫폼 전체 누적 호출 수를 계정의 일일 한도로 해석하지 않는다.
   키 미발급 상태의 현재 검수는 이 확인을 대체하지 않는다.
3. 시작 범위/일일 건수를 정하고 검증 사실이 있을 때만 `MESSAGE_COLLECTION_CONTRACT_VERIFIED=true`,
   `MESSAGE_COLLECTION_ENABLED=true`를 설정한다. AI/피드 연결 및 세 고정 버전이 없으면 배포 설정 검증이 실패한다.
   `MESSAGE_ANALYSIS_DAILY_LIMIT=20`, `MESSAGE_COLLECTION_MAX_PAGES=4`, `MESSAGE_COLLECTION_CATCHUP_DAYS=7`,
   `MESSAGE_COLLECTION_INTERVAL_MINUTES=15`, `MESSAGE_FEED_REQUEST_LIMIT=450`이 기본값이다.
   조회 주기는 15/30/60분, 회당 페이지는 1~4, 공통 조회 상한은 1~450 범위다. 더 빠른 주기는 먼저 실제 제공자 한도/조회 전략을 다시 검토한다.
   `MESSAGE_COLLECTION_START_AT`은 선택값이며 최초 활성화 전에만 과거 범위를 바꿀 수 있다. 미래 시각은 수집 오류가 된다.
4. 별도 배포 요청 후 새 비공개 서비스·OIDC·정규 예약 실행·상태·원문/분석 저장을 제한적으로 확인한다.
   기존 KMA 예약 실행/알림 실적은 시험에 사용하지 않는다.

비활성 배포는 새 문자 예약 작업 두 개만 일시정지한다. 조회 권한 오류를 `작업 없음`으로 숨기지 않고 실패한다.
이미 저장된 기록·대기열·한도 집계는 삭제하지 않는다. 진행 중인 실행은 끝날 수 있으며 과거 원문을 자동으로 재결제하지 않는다.

## 제한 운영 배포와 관찰 기준 (2026-11-08 승인)

- 배포 워크플로에 위 15분/4페이지/450회/AI 20건과 고정 버전 1의 활성화 기본값을 기록한다.
  GitHub 저장소 변수는 이 값보다 우선한다. 명시적 `MESSAGE_COLLECTION_ENABLED=false`는 문자 예약 두 개를 멈춘다.
  로컬 앱/설정 생성기의 무설정 기본은 계속 비활성이다. 별도 GitHub 변수 권한 확장은 필요하지 않다.
- SafetyData [명세/이용허락](https://www.safetydata.go.kr/disaster-data/view?dataSn=228)과
  [약관](https://www.safetydata.go.kr/utztnTrms)을 대조했다. `crtDt`는 조회 시작일자이며 범위 응답도 처리한다.
  출처·공식 원문은 그대로 보존하고 AI 해석/사람의 검토는 별도 기록으로 구분한다.
  공공누리 제3유형 안내를 확인했으며 원문을 변경한 공식 문자로 재배포하지 않는다.
  공개 안내에서 확정 보관 일수나 제공 지연 SLA는 확인하지 못했다. 내부 시범 범위와 지연 표시를 유지한다.
- 필수 검수: 전일 포함 제한 API 조회, 운영 Firestore 상태/한도 저장, IAM 비공개 worker, 두 OIDC 정규 예약,
  창작 예문 1건의 예약 분석 → 저장 → 새 화면 검토/보류·확정/복사·복구, 기존 KMA 상태 대조.
  브라우저에서 분석 요청 없이 다음 정규 분석 예약이 예문을 처리하게 한다. 예문을 실적으로 집계하지 않는다.
- `Verify message release`의 `mode=verify`는 명시한 창작 예문만 등록/대기열에 넣고 검토한다.
  실패 시 결과의 record ID를 넣어 같은 예문으로 재개하고, 불확실한 분석을 자동 재결제하지 않는다.
  `mode=status`는 로그인 뒤 상태·기록 개수만 읽고 정상 수집 완료/상한/예약 설정을 확인한다.
  임시 검수 서비스에는 관리자 비밀번호만 연결하며 키 값은 결과나 작업공간으로 가져오지 않는다.
- 사용 중에는 수집 정상 시각, 대기/실패/한도, 검토 때 고친 위치/대상/문구와 보류 이유를 관찰한다.
  다음 기능은 후속 문자 제안·변경 비교다. 실제 자동 연락/발송·현장 회신은 별도 범위로 유지한다.
