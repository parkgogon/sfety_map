## 1. 목적과 이번 범위

공식 재난문자 중 소관시설과 현장 업무에 관련된 새 정보를 골라 기존 직원 단체 Telegram방에 자동 공유한다.
일반적인 건마다 관리자가 페이지를 열어 승인하는 단계를 요구하지 않는다. 관리자는 전파 이력과 예외를 확인한다.
직원별 수신 매핑·현장 회신 수집·피해/안전 판정·대피 경로 생성은 이번 범위에 넣지 않는다.
기존 정형 KMA 특보의 규칙·기준 상태·5분 감시는 그대로 운용한다.

| `telegram.py`: 공통 발송 어댑터. 현재 성공/실패만 반환 | 전파용 결과는 성공·명확한 거절·결과 미상을 구분하고 성공 시 Telegram message_id를 보존한다 |
| KMA outbox는 기상 배치/기존 재시도 정책에 연결됨 | 전송 어댑터는 재사용하되 문자 판단/전파 이력은 별도로 둔다. KMA dispatch로 문자 전파를 우회하지 않는다 |
| 문자 worker에는 Telegram 키가 연결되지 않음 | 후속 발송 단계에서 기존 봇/직원방·관리자방 설정을 서버에 연결한다. 모델 입력이나 브라우저로 전달하지 않는다 |

시설에는 주소와 KMA 지역 코드가 있다. KMA 코드가 곧 행정구역이라고 가정하지 않는다.
지역형 판단에는 원문에서 확인한 지역과 시설 주소의 검증된 대응이 필요하며, 지도 대표점 반경으로 광역 지역을 대체하지 않는다.

## 3. 입력 → 판단 → 처리

### 3.1 서버가 먼저 확인하는 입력

- 공식 출처·원문·발행 시각·수신지역·ID/버전/관측 시각을 분리해 보존한다.
- 같은 버전을 다시 관측하면 저장된 판단을 재사용한다. 수동/창작 예문은 운영 자동전파 대상이 아니다.
- 원문 정정은 새 버전이다. 분석/전파 직전에도 현재 버전과 일치하는지 확인한다.
- 원문의 실제 상황 지역을 우선한다. 수신지역을 발령기관 또는 사고 지점으로 바꾸어 해석하지 않는다.
- 전파 활성화 이전 자료·발행 시각 미상/비정상·오래된 대기 자료는 현재 긴급 상황으로 자동 전파하지 않는다.
  이력과 확인 필요 사유는 보존한다. 자동전파의 구체적 신선도 제한은 3단계에서 정하고 예정 상황의 유효 기간을 따로 다룬다.

### 3.2 AI가 반환할 판단 계약 — 초안

기존 상황 해석과 같은 분석의 최종 제출에 `notification_assessment`를 추가한다.

| 필드 | 값/의미 |
| --- | --- |
| `need` | `notify` 전달 필요 / `record_only` 기록 / `uncertain` 판단 불명확 |
| `urgency` | `immediate` 현재 신속 공유 / `scheduled` 예정 상황 / `reference` 참고 / `unknown` 미상 |
| `relevance` | `facility` 특정 소관시설 / `nearby` 주변 시설 / `area_operations` 지역 운영·접근 / `general` 일반 안내 / `outside_scope` 업무 범위 밖 / `unknown` 미상 |
| `reason` | 판단 이유 1~2문장. 확인한 사실과 미확인 내용을 구분 |
| `evidence` | 판단의 근거가 되는 원문 그대로의 인용. 원문의 부분 문자열인지 서버가 검사 |
| `basis_refs` | 실제 조회한 장소 후보·시설 또는 검증한 지역 조회 결과의 참조 ID |

짧은 상황 문장은 기존 `summary/parts`를 사용한다. 시설명·거리·좌표·수신방을 AI가 자유 문장으로 생성하지 않는다.
`need=notify` 자체는 발송 권한이 아니다. 서버가 근거·시각·버전·자료 상태를 검증해 최종 처리를 정한다.
자신감 점수만으로 발송을 허용하지 않는다. `record_only`도 근거가 부족하면 확인 필요로 남긴다.

### 3.3 관련성 확인의 분기

1. **특정 지점형**: 원문 고유 지명/시설명 검색 → 역할·지역·주소·장소 종류 대조 → 검증된 후보 주변 시설 조회.
   기존 3km는 주변 참고 조회의 초기값이며 위험 범위나 자동 발송의 유일 기준이 아니다.
2. **지역형**: 단수·정전·통제·대피 등 지역 전체의 상황 → 원문의 범위와 시설의 소속/운영 관련성을 확인.
   좌표나 반경 안 시설 수가 없어도 전달 가능하다. 지역 조회의 모호함은 그대로 남긴다.
3. **일반 안내형**: 구체적인 현장 업무 정보가 있는지 확인. 명확한 일반 안내는 장소 검색 없이 마칠 수 있다.
4. **해제/정정형**: 구간별로 해제·유지를 보존한다. 확인된 이전 전파와 연결할 수 있을 때만 변경 관계를 표시한다.
   연결되지 않은 문자를 같은 사건으로 추정하거나 모든 시설이 안전하다고 바꾸지 않는다.

산업단지/산/도로 대표점은 그 성격을 표시한다. 대피 목적지·학교 운동장을 사고 기준점으로 사용하지 않는다.

### 3.4 최종 처리표 — 서버 책임

| 조건 | 결과 | 직원 단체방 | 관리자 |
| --- | --- | --- | --- |
| 전달 필요 + 검증된 업무 관련 근거 + 현재 유효한 원문 | `notify_ready` | 핵심 요약 자동전파 | 내역 조회 |
| 전달 필요는 분명하나 정확한 위치/시설 정보만 부족 | `notify_source_only` | 원문 중심 안내 + 미확인 사항. 시설/거리 추정 없음 | 상세 확인 가능 |
| 업무 관련성이 낮거나 새로 알릴 정보가 없다는 근거가 충분 | `record_only` | 발송 없음 | 사유 조회 |
| 의미/업무 관련성 자체가 불명확하거나 근거 검증 실패 | `attention_required` | 추정 요약 발송 없음 | 예외 알림 |
| AI 장애/한도 도달 | `analysis_unavailable` | 검증된 긴급 원문 대체 기준에 맞는 경우만 원문 전달 | 장애/대기 알림 |
| 저장소/현재 버전 검증 실패 | `blocked` | 새 발송 보류 | 저장·버전 오류 표시 |

`notify_source_only`는 AI가 전달 필요성과 업무 관련성을 해석했지만 공간 정보만 부족한 경우다.
`analysis_unavailable`은 AI의 해석이 없는 경우로 구분한다. 대체 전파는 공식 출처/대상 지역/현재 시각과
직접적인 긴급 행동 문구 등 확인 가능한 조건을 별도 정책으로 검증한다. 현재 저장 필드에 공식 긴급 등급이 있다고 가정하지 않는다.
대피라는 단어 하나로 분기하지 않으며 예방·훈련·예정·해제·부정 문구를 구별하는 예문 검증이 필요하다.
불명확한 대체 판단은 관리자 예외로 남긴다. 장애 알림은 묶어 알려 같은 오류로 단체방을 반복 채우지 않는다.

## 4. 보낼 내용과 상태 기록

- 1개 메시지에 상황 1~2문장, 원문 발행 시각, 참고 지역/시설, 확인된 거리, 미확인 사항, 직원용 지도 링크를 넣는다.
- 시설은 최대 3개와 나머지 개수만 표시하는 초기안이다. 거리는 서버 계산값이며 대표점/직선 기준을 함께 표시한다.
- 시설 0개소·위치 미상은 `안전`으로 표현하지 않는다. 없는 항목을 채워 넣지 않는다.
- 링크는 직원이 접근 가능한 현장 지도/공개 출처를 사용한다. 관리자 전용 문자 기록 페이지를 직원용 링크로 대신하지 않는다.
  개별 원문 URL이 없으면 일반 출처 페이지를 해당 문자 원문 링크로 표시하지 않는다.
- 수신방은 서버의 기존 직원 단체방으로 고정한다. 운영 장애는 기존 관리자방으로 구분한다.
- 자동 판단/발송 상태는 `review_state/review_completion`과 별도로 둔다. 자동전파가 사람의 검토·현장 확인 실적이 되지 않는다.
- 원문 버전·분석 버전·정책 버전·시설 자료 식별값·판단 이유·최종 발송문·발송 시도/결과를 보존한다.
- 성공 응답을 확인하기 전에는 성공 처리하지 않는다. 시간 초과 등 결과 미상은 명확한 거절과 구분한다.
  Telegram의 중복 없는 1회 전달을 보장한다고 주장하지 않는다. 미상 결과를 반복 재시도하지 않고 예외로 기록한다.
- 같은 공식 버전의 중복 실행은 하나의 전파 작업을 사용한다. 재분석·재시작·정책 변경만으로 기전파 자료를 다시 보내지 않는다.
  정정은 별도 전파 판단 대상이며, 전파 대기 중 원문이 바뀌면 이전 버전의 대기 전파를 무효화한다.

## 5. 예문별 기대 결과 — 모두 창작/가짜 시설 자료로 검증

| 사례 | 확인할 근거/조건 | 기대 결과 |
| --- | --- | --- |
| 1. 산업단지 화재·연기 발생 | 지역 일치 대표점, 주변 소관시설 2개 확인 | 요약 + 주변 참고시설·대표점 기준 거리 전파 |
| 2. 소관시설이 있는 지역 전역 단수 | 원문 범위와 시설 주소 대응 확인 | 지역 운영 관련 전파. 사고 지점 좌표 불필요 |
| 3. 매일 반복되는 일반 건강 안내 | 구체적인 현장 업무 정보 없음 | 기록, 판단 이유 보존 |
| 4. 같은 ID/원문의 재조회 | 처리/발송된 버전과 동일 | 새 AI 호출/새 발송 없음 |
| 5. 같은 공식 ID의 통제 구간 정정 | 새 원문 버전과 변경 근거 | 정정 내용을 재판단. 이전 대기 발송 무효화 |
| 6. 일부 구간 해제·다른 구간 통제 유지 | 원문에 두 구간 명시 | 두 상태를 함께 전달. 전체 해제 표현 금지 |
| 7. 화재 장소 미상·소관 지역의 현재 대피 지시 | 전달 필요/업무 관련성은 명확, 정확한 지점 미상 | 원문 중심 전파. 임의 기준점·시설·거리 없음 |
| 8. 어느 도시인지 모르는 중앙동 사고 | 수신지역 여러 곳, 실제 도시 불명 | 확인 필요. 임의의 도시/주변 시설로 대체하지 않음 |
| 9. 사고지와 대피소가 함께 있는 문자 | 장소 역할이 다름 | 사고지 주변만 참고 조회. 대피소 거리를 사고지 거리로 쓰지 않음 |
| 10. 내일 09~18시 예정 통제 | 발행 시각 기준 내일 해석 가능, 운영 관련성 확인 | 예정 표시로 전파. 현재 통제로 바꾸지 않음 |
| 11. 소관 지역 밖 사고가 소관 지역에도 수신됨 | 본문 실제 사고 지역과 업무 관련성 확인 | 수신지역만으로 주변 시설을 만들지 않음. 관련성 낮음이 명확하면 기록 |
| 12. AI 실패/한도 소진 때 긴급 지시와 일반 안내 | 검증 가능한 대체 정책의 긴급/해제/훈련/일반 예문 | 정책에 맞는 긴급 원문만 대체. 그 외 관리자 예외/지연 알림 |
| 13. 전파 대기 중 원문 정정/분석 근거 변경 | 전파할 버전과 현재 버전 불일치 | 오래된 전파 차단, 최신 판단 필요 |
| 14. AI가 존재하지 않는 시설/거리/인용을 제출 | 조회 결과/원문과 불일치 | 검증 실패. 잘못된 내용 전파 없음 |
| 15. Telegram 거절/429/응답 시간 초과 | 제공자 응답별 가짜 결과 | 거절·대기·결과 미상 분리. 미상을 성공 또는 무조건 재시도로 바꾸지 않음 |
| 16. 실제 직원 수신 화면 | 관리자 로그인 권한 없는 직원 | 지도 접근 가능. 관리자 전용 기록 링크를 필수로 요구하지 않음 |

3km 밖이라는 사실 하나로 기록 처리하지 않는다. 특정 시설 직접 언급·광역 운영 영향은 별도로 확인한다.
이 표의 판정은 창작 입력과 가짜 도구 결과를 세트로 고정한 테스트의 기대값이다. 실제 모델의 정확도 실적으로 세지 않는다.
1단계에서는 사례 1·2·3·6·7·8·9·10·11·14와 직원 링크 형식을 검증했다.
사례 4·5·13의 버전/읽기 경계와 전파 작업의 중복 준비/정정 무효화/중단 복구는 2단계에서 검증했다.
실제 Telegram 수신 중복/응답 미상 처리는 4단계이며 준비 저장의 중복 방지와 구분한다.
사례 12의 현재 대피 원문 대체/일반 예외/한도·비용 경계는 3단계에서 가짜 제공자로 검증했다. 사례 15의 실제 전송 결과 처리와
사례 16의 실제 수신자 접속은 4단계 검수다. 16개 운영 사례를 모두 완성했다고 표시하지 않는다.

## 6. 구현 순서와 단계별 수용 조건

| 단계 | 범위 | 완료 조건 |

실제 모델 평가는 호출/토큰 측정이며 자동 테스트 결과와 구분한다. 현재 작업은 그 평가나 운영 배포를 실행하지 않는다.

## 7. 수집 주기와 비용 — 로컬 구현, 운영 전환 전 확인

- 현재 운영은 기존 15분이다. 새 `MESSAGE_COLLECTION_FAST_ENABLED=true`와 간격 5분을 함께 설정하면 최신 우선 전략/예약을 사용한다. 로컬 코드 구현과 운영 설정 변경을 구분한다.
- 오늘 자료 5분·전일 자료 1시간은 **각 조회가 1페이지일 때** 하루 312회라는 초기안이다.
  추가 페이지·첫 페이지 재검증·실패·수동 요청도 450회 공통 한도에 포함하고, 최신 자료 몫을 남겨 보충 조회를 조절한다.
  보충 페이지가 남아도 새 자료 첫 페이지가 계속 뒤로 밀리지 않아야 한다. 공개 자료 제공 지연은 별도 관측한다.
- 하루 20건은 현재 제한 운영값이다. 자동전파 목표를 충족한다고 가정하지 않으며, 처리량·토큰 측정 후 일일 건수/월 예산을 정한다.
- 동일 원문 재조회와 발송 재시도에는 유료 재분석을 하지 않는다. 실패/응답 미상 유료 시도는 함부로 환급·재시도하지 않는다.
- `usage_snapshot()`의 프로세스 누적치와 별도로 `message-spend-*` 영속 원장을 구현했다. `MESSAGE_AI_SPEND_BUDGET_ENABLED=true`일 때만 요청 전 예약/응답 후 정산을 적용한다.
  `MESSAGE_AI_DAILY_BUDGET_CENTS=100`, `MESSAGE_AI_MONTHLY_BUDGET_CENTS=2000`은 달러 센트 정수다. 운영 전환 전에 실제 처리량과 함께 확정한다.
- 기존 예문 6건 평균은 캐시 할인 전 약 $0.011/건(현재 모델 단가 적용)이다. 실제 새 판단 출력/운영 문자 처리량의 보장값이 아니다.

## 8. 첫 구현을 끝냈다고 볼 기준

**하나의 입력과 가짜 조회 결과를 주면, 왜 전달/기록/확인 필요인지와 실제로 보낼 미리보기가 재현된다.**
원문 근거·지역·시각·시설 자료가 부족할 때 추정으로 채우지 않고, 기존 검토 기록도 유지해야 한다.
이 경계까지 구현한 뒤 판정 예시를 검토하고 2단계로 진행한다. 함수/파일 분할이나 인프라 확장은 이 목표에 필요한 만큼만 정한다.
