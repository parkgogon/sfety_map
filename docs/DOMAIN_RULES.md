# 도메인 규칙

- 문서 상태: v3 초기 정책
- 대상 버전: v3
- 목적: UI나 외부 API가 바뀌어도 동일하게 유지할 업무 규칙 정의

## 1. 용어

| 용어 | 정의 |
|---|---|
| 시설 | 관제 대상이 되는 물리적 장소. 고유 ID와 좌표를 가짐 |
| 특보 | 기상청이 특정 특보구역에 발표한 기상 위험 정보 |
| 특보구역 | 기상청 `region_code`로 식별되는 공식 공간 경계 |
| 영향 시설 | 하나 이상의 활성 특보구역과 매칭된 시설 |
| 위험도 평가 | 영향 시설에 대해 등급·근거를 계산한 결과 |
| 점검 대상 | 위험도 또는 정책에 따라 확인 행동이 필요한 시설 |
| 데이터 상태 | 실시간, fallback, 지연, 오류, 모의훈련을 구분하는 상태 |

## 2. 표준 데이터 모델

도메인 계층은 pandas `Series/DataFrame`을 직접 받지 않습니다.

### Facility

```text
id                 필수, 변경되지 않는 고유 식별자
name               필수
facility_type      필수
latitude           필수
longitude          필수
region_code        권장, 공식 행정/특보구역 코드
is_monitored       필수, 관제 대상 여부
department         선택
manager_name       선택
manager_contact    선택, 민감정보
```

시설명은 표시값이며 식별자로 사용하지 않습니다.

### Warning

```text
id                 source + region_code + type + issued_at 조합
source             예: KMA
region_up_code     필수
region_code        필수
region_name        표시용
warning_type       필수
level              ADVISORY / WARNING / CRITICAL / UNKNOWN
command            발표·변경·해제 등 원본 명령
issued_at          발표 시각
effective_at       발효 시각
```

### WeatherObservation

```text
facility_id
observed_at
temperature_c
rainfall_1h_mm
wind_speed_ms
wind_direction_deg
status
```

숫자 조회 실패를 `"-"` 문자열로 표현하지 않고 nullable 숫자와 상태로 분리합니다.

### RiskAssessment

```text
facility_id
grade              HIGH / MEDIUM / LOW / NONE / UNASSESSED
matched_warning_ids
reasons
policy_version
assessed_at
```

## 3. 데이터 상태

| 상태 | 의미 | UI 행동 |
|---|---|---|
| LIVE | 최신 API 응답 | 정상 표시 |
| FALLBACK | 공식 경계 내장본 사용 | 작은 안내 표시, 계산 가능 |
| STALE | 마지막 성공 데이터가 허용 시간 초과 | 경고 표시, 신규 수동 전파·PDF 차단 |
| ERROR | 사용할 수 있는 데이터 없음 | 위험도 계산 중단, 정상 0건 표시 및 신규 수동 전파·PDF 금지 |
| SIMULATION | 훈련 데이터 | 모든 화면과 보고서에 훈련 표시 |

권장 신선도 기준은 다음과 같으며 운영 합의 후 확정합니다.

- 특보: 캐시 10분, 20분 초과 시 STALE 제안
- 경계: 캐시 24시간, 내장본 사용 가능
- 시설 기상: 캐시 10분, 선택 시 조회

## 4. 특보 정규화

1. provider는 KMA 원본을 표준 `Warning`으로 변환합니다.
2. 알려진 단계 문자열은 enum으로 정규화합니다.
3. 알 수 없는 특보 종류·단계는 버리지 않고 `UNKNOWN`으로 유지합니다.
4. 해제된 특보 포함 여부는 API 계약 테스트로 고정합니다.
5. 중복 ID의 특보는 한 번만 유지합니다.
6. 관제 권역은 표시 이름이 아니라 코드 또는 시설의 `is_monitored`로 결정합니다.

## 5. 시설과 특보 매칭

우선순위는 다음과 같습니다.

1. 시설 좌표가 공식 특보구역 polygon에 포함되면 매칭
2. 경계선 위 시설은 포함으로 처리
3. polygon이 유효하지 않으면 복구 후 재시도
4. 공식 공간 정보가 없을 때만 `region_code` 직접 비교
5. 코드도 없을 때만 주소 문자열 fallback

평가 결과에는 `polygon`, `region_code`, `address_fallback` 중 어떤 근거를
사용했는지 기록합니다.

시설 하나가 여러 특보구역에 매칭될 수 있으며 모든 매칭 특보를 보존합니다.

## 6. 위험도 정책

v3는 기존 숫자 가중치와 합산 점수를 사용하지 않습니다. 실제 적용표는
`safety_dashboard/config/risk_policy.toml` 한 곳에서 관리합니다.

### 확정 규칙

1. 정책 파일은 특보 종류와 단계 조합을 등급에 직접 연결합니다.
2. 숫자 곱셈식 대신 사람이 그대로 읽을 수 있는 표를 사용합니다.
3. 여러 특보가 겹치면 등급 rank가 가장 높은 결과를 최종 등급으로 합니다.
4. 여러 특보를 합산하지 않습니다. 지역 중복 발표가 위험을 과대평가할 수 있기
   때문입니다.
5. 결과에는 최종 등급뿐 아니라 모든 매칭 특보와 각각의 정책 결과를 남깁니다.
6. 정책에 없는 특보 종류·단계는 LOW가 아니라 UNASSESSED로 분류합니다.
7. 정책 파일에는 `version`과 설명을 포함하고 보고서에 정책 버전을 표시합니다.
8. 시설 취약도는 v3 첫 배포에서 반영하지 않습니다.
9. 화면에서 특보 종류×단계 등급을 임시 편집할 수 있으며, 변경값은
   현재 브라우저 세션에만 유지합니다.
10. 세션 정책은 기본 정책 버전과 행렬 해시를 결합한 버전을 사용하고,
    Telegram과 PDF에 임시 기준임을 표시합니다.
11. 기본 기준으로 되돌리기나 새 브라우저 세션을 시작하면 TOML 기준으로
    돌아갑니다.

정책 파일 예시는 다음과 같습니다.

```toml
[warning_types."호우"]
ADVISORY = "MEDIUM"
WARNING = "HIGH"
CRITICAL = "HIGH"

[warning_types."폭염"]
ADVISORY = "LOW"
WARNING = "MEDIUM"
CRITICAL = "HIGH"
```

## 7. 등급별 행동

| 등급 | 제안 의미 | 제안 행동 |
|---|---|---|
| HIGH | 즉각적인 피해 가능성 | 즉시 점검 요청, 관리자 확인 |
| MEDIUM | 주의가 필요한 영향 | 담당자 확인 요청 |
| LOW | 영향권 포함 | 경과 관찰 |
| NONE | 활성 특보 영향 없음 | 행동 없음 |
| UNASSESSED | 규칙 또는 데이터 부족 | 관리자 수동 판단 |

알림 대상과 위험도 등급은 동일 개념으로 가정하지 않습니다. 예를 들어 모든
경보 시설을 알림 대상으로 하되 위험도는 시설 취약도까지 포함할 수 있습니다.

## 8. 알림 규칙

1. 자동 작업자는 공식 KMA 특보를 5분마다 확인하고 시설 영향의 발효·격상·해제
   변화만 전파합니다. 정상 무변화 상태를 반복 전송하지 않습니다.
2. KMA 조회 실패는 해제로 해석하지 않고 이전 기준 상태를 보존합니다.
3. 자동 기준 상태에는 서버 기본 정책만 사용하며 모의훈련·브라우저 임시정책을
   섞지 않습니다.
4. 수동 상황전파는 현재 영향시설을 대상으로 재공지·정정·추가안내·훈련 목적을
   명시하고 사용자가 최종 확인한 뒤 발송합니다.
5. 메시지에는 시설, 등급, 적용 특보와 정책 버전을 포함합니다.
6. Telegram 길이 제한을 넘으면 시설을 누락하지 않고 여러 메시지로 분할합니다.
7. 동적 문자열은 Telegram HTML 규칙에 맞게 escape합니다.
8. 일부 메시지만 성공하면 부분 실패로 보고하고 outbox에서 제한 시간 동안
   재시도합니다.
9. 자동·수동·시험·훈련 결과는 Firestore에서 서로 다른 실적으로 기록합니다.
10. 관리자방은 시스템 상태, 시설담당자 그룹은 시설 특보 전파에 사용합니다.

## 9. 보고서 규칙

- 화면과 같은 `RiskAssessment` 결과를 사용합니다.
- 별도의 위험도 재계산을 하지 않습니다.
- 데이터 기준 시각과 상태를 표시합니다.
- 모의훈련 보고서에는 모든 페이지에 훈련 표식을 표시합니다.
- 데이터 오류 상태에서는 정상 보고서를 생성하지 않습니다.
- 섹션은 `관제 요약 → 영향시설 우선순위 → 활성 특보` 순서를 사용합니다.
- 표가 여러 페이지로 나뉘면 섹션 문맥과 표 헤더를 반복합니다.

## 10. 민감정보

- API 키와 Telegram 토큰은 환경변수 또는 secrets에서만 읽습니다.
- 담당자 연락처는 로그·오류 메시지에 기록하지 않습니다.
- 화면·보고서·Telegram은 담당부서와 담당자 이름/직책만 표시하고
  휴대전화 번호는 노출하지 않습니다.
- 테스트 데이터에는 실제 토큰과 실제 연락처를 사용하지 않습니다.
